## 阶段 B：体检口径修正

改动（需求 5.1～5.3）：

- 新增 `src/maintenance/diagnostics.js`：只做测量，不碰界面。分类（`classifyRequest`）、单笔描述（`describeRequest`）、按类汇总（`summarizeRequests`，耗时取并集）、接收速率估计、脱敏报告（`buildDiagReport`、`redactUrl`）、覆盖缺口（`diagGaps`）。
- 启动完成（APP_READY）的时间改由测量模块在加载时自己监听；新版酒馆对晚注册的监听会立即补发，这种情况识别为「本扩展加载时酒馆已启动完成」，不记时间。
- `src/ui/health.js` 只负责显示：时间点表、请求分类表、时间线、单笔最长、明细、导出。
- 请求类别：设置及预设、全部角色列表、单张角色详情、聊天记录、扩展清单、扩展脚本与样式、世界书、头像与背景、设置保存、第三方快速接口（其他）、酒馆程序文件、其他接口、外部网站。柏宝库、鸡尾酒+ 的快速接口路径取自它们的源码（柏宝库 0.6.4、鸡尾酒+ 0.1.24、柏宝箱 1.0.0），归到对应类别并注明提供者。
- 去掉的错误推断：小请求耗时长判为排队；角色详情当成重复的角色列表；`encodedBodySize` 冒充实际传输；把接收速率称为服务器速度；把启动时的设置保存归到某个扩展；清理页「打开约快 X 秒」。
- 新增明细与导出：报告包含扩展版本、浏览器大类和系统大类、统计口径定义、各类汇总、每笔请求（路径已脱敏）、内存中预设大小（按类型汇总，不含预设名）、扩展设置数据量、覆盖缺口。

影响范围与降级：只影响「加载体检」页、清理页的估算文案。体检仍只在打开该页时运行；页面加载时只多注册一个 APP_READY 监听，不轮询、不发请求。

测试（真实结果）：

- `node test/run-core.cjs`：39 项通过，6 项跳过。新增 4 项：分类、体积口径和跨域、并集、报告脱敏。
- `bash test/run-browser.sh`：12 个检查全部通过。`test/clean-check.mjs` 的体检部分按新口径改写，并检查明细和导出的报告里没有角色文件名。
- 手机宽度（390px）截图检查过请求表和时间线的排版。

已知限制：

- 「聊天可操作」没有实现测量。酒馆没有可靠的「聊天已可操作」事件；鸡尾酒的「提前解除遮罩」会让界面比实际就绪更早出现，用遮罩消失时间也不可靠。

避让规则的落实：本扩展本轮没有新增任何请求接管、fetch／XHR 补丁、Service Worker 注册或启动桥接，所以「同一请求只允许一个接管者」对本扩展自动成立；卡片只负责把其他扩展之间的重叠指出来，由用户自己决定保留哪个。

关于「推荐配置」：需求要求只有已验证、无重叠的本扩展选项才能预勾选。本扩展目前没有自己的加速选项（见阶段 D 的结论），所以推荐列表为空，两个按钮显示为不可用并写明原因，而不是放一个点了没有效果的按钮。

独立设置字段：维护模块目前没有需要保存的设置，所以没有写入新的设置字段；以后加选项时使用独立的 `extensionSettings.presetAtelierMaintenance`，不和预设模块的 `presetAtelier` 混用。

- 新增 `test/compat-check.mjs`：没有加速扩展时不发请求、显示未发现；模拟柏宝箱、柏宝库、鸡尾酒在运行，检查各列状态、版本等级、重叠提示（只对三项读取类判断），检查前后 `extensionSettings` 完全一致，导出的诊断报告带上检查结果。

## 阶段 D：读取加速——必要性判断（本轮未开发）

需求 7.1 要求先比较「启用和停用现有加速」时的实际请求，确认「未变化的预设仍大规模重复传输」且现有提供者缺少这个能力，才开发增量读取。本轮的结论：

**还不能下结论，所以没有开发。** 这个比较需要在用户自己的酒馆、数据和设备上做，本轮的开发环境里没有真实酒馆，也没有用户的 18 MB 预设，测不了。

只读源码得到的线索（不是测量结果）：

- 柏宝库 0.6.4 的 `settings/fast-get`：服务端缓存设置文件的读取和拼装结果，减少服务器处理时间；浏览器端的缓存（`frontendCache`）只在同一次页面里去重，刷新页面后不保留。每次打开仍会把完整的设置和全部预设传一遍。
- 鸡尾酒+ 0.1.24 的 `fast/settings-get`：服务端缓存和启动时提前发出请求（预取）；保存时按差异上传。读取同样每次完整传输，没找到跨页面保留预设的浏览器缓存。
- 鸡尾酒 0.1.17：预取、去重角色列表等请求，提前解除遮罩，不涉及设置和预设的传输量。

所以从源码看，「未变化的预设每次打开都完整传输」很可能在开着这些加速时仍然存在，但这一点必须用实测确认。

### 实测步骤（用 1.9.0 的体检）

1. 固定服务器、设备（建议先测最常用的手机）、网络、数据和扩展开关。
2. 分三种情况，每种打开酒馆至少 3 次，每次打开后进「更多 → 加载体检」，点「导出诊断报告」：
   - 甲：关掉柏宝箱的「Settings get/save 加速」和鸡尾酒+（只留酒馆原流程）；
   - 乙：只开柏宝库／柏宝箱的设置加速；
   - 丙：只开鸡尾酒+。
3. 每份报告看 `categories` 里 `cat: "settings"` 的 `transfer`（实际传输）、`decoded`（解压后）、`busy`，以及 `timing.appReady`。每种情况取中位数和范围；网络波动大时注明不能下结论。
4. 判断：
   - 乙、丙第二次及以后打开时，设置请求的实际传输仍接近甲（比如超过甲的 70%），而且全部预设占了设置文件的大头 → 缺口存在，可以进入增量读取开发；
   - 乙或丙的实际传输已经明显变小（例如命中了缓存、只传了变化的部分）→ 交付检测和引导即可，不再套一层缓存。

### 如果确认要开发（设计要点，供下一轮评审）

- 需要服务端配合：普通前端扩展执行时，最早的设置读取已经发生。可行的路线是在现有提供者（柏宝库或鸡尾酒+）的启动桥接上增加能力，或者单独提供一个明确安装、可卸载的后端插件，并说明它与现有桥接如何分工；不偷偷注入第二套启动桥接。
- 版本清单由服务端从已认证会话确定账号，按预设文件生成内容指纹，利用服务端已有的缓存和失效机制，不为生成清单每次重新解析全部大文件。
- 浏览器端缓存放在本扩展自己的 IndexedDB 库里，键包含服务器实例、账号、数据类型、预设名、协议版本；只作为加速副本，不当备份，不写回服务器，不缓存认证令牌、密钥。
- 清单和正文之间发生更新时重新校验，或退回完整读取；缓存损坏、配额不足、认证失效、版本不符时退回正常读取。
- 初版不缓存聊天，不接管任何写入。

### 安装、停用和恢复

- 安装和更新方式不变：扩展管理里「更新」，或扩展页设置框里「检查更新」。
- 本版本没有新增设置字段，草稿、备份、方案、站点的保存格式都没变，可以直接回到 1.8.0。
- 「加载与兼容」卡片和体检不接管任何请求，没有需要停用的加速；停用整个扩展用扩展管理里的开关即可，停用后不会留下 fetch 补丁、Service Worker 或启动桥接。
- 回到 1.8.0：在服务器上进入 `public/scripts/extensions/third-party/Burnt-chicken-wings`（或对应的用户扩展目录），执行 `git checkout cef27cc`，刷新酒馆。要回到最新版，在同一目录执行 `git checkout main && git pull`（处在旧版本时扩展管理里的「更新」可能失败）。

## 后续拆分的准备情况（需求 12）

本轮按需求不拆仓库。目前的边界：

| 模块 | 文件 | 说明 |
| --- | --- | --- |
| 预设工作 | `src/core/*`、`src/ui/organize.js`、`suture.js`、`cotview.js`、`schemes.js`、`apiview.js`、`cleanup.js`（预设归档、删除）、`state.js`、`theme.js` | 设置字段 `presetAtelier`，IndexedDB `preset-atelier` |
| 维护与加载 | `src/maintenance/diagnostics.js`、`compat.js`、`card.js`，`src/ui/health.js`（体检页），`src/ui/cleanmore.js`（扩展数据、角色卡、世界书清理） | 目前没有自己的设置字段和存储 |
| 共享 | `src/host.js`（宿主访问）、`src/ui/dom.js`（弹窗、提示） | 两个模块都通过这里调用 |

拆分前还要处理的耦合：

- `cleanmore.js` 的「本地备份」一栏读写的是预设模块的备份库，拆分时这一栏应留在预设扩展里。
- 体检的「去清理」按钮跳到预设模块的清理页；拆分后改成提示文字或跨扩展打开。
- 体检统计预设大小时用了 `readPreset`（在 `host.js`），拆分时一起复制到新扩展的共享部分。
- 两个模块都挂在同一个面板和设置框里；拆分时新扩展需要自己的入口，旧扩展在检测到新扩展后不再显示维护页面（同一功能只允许一方运行）。
